# MyManabi 仕様

学習フロー、理解度測定、教材管理、学習履歴、レポート、データ配置などの具体仕様を記録する。背景の目的・方針は [コンセプト（concept）](../concept/README.md) を参照。

実装順と、最初に検証する小さな縦切りは [初期 PoC ロードマップ](initial-poc-roadmap.md) を参照。

出題選定、評価プロトコル、保護者の関与に関する中核ドメインは [出題選定・評価・保護者関与のドメイン設計](domain-design.md) を参照。

教科書、PDF プリント、問題集から教材を取り込む際の探索仕様は [教材取り込みの探索仕様](content-import.md) を参照。

## 1. 学習の基本フロー

### 1.1 通常学習

- 原則として教科書順に進む
- 起動時に選択肢を並べすぎず、前回の学習経路を引き継ぐ
- 学習終了時に本人へ表示するのは、今日取り組んだ問題数、正答数、続けるかどうかだけ
- ランキング、連続学習日数、過剰な称賛などのゲーム化は初期版に入れない

初回学習では、本人が適切な学習順序を判断できるとは限らないため、教科書順を基本とする。一方、復習やテスト対策では目的に応じて経路を変える。

### 1.2 問題への回答

各問題では、通常回答に加えて次の操作を用意する。

- `分からない`
- `納得できない`

`分からない` と誤答は分けて保存する。本人が理解できないことを明示した場合と、回答した結果として誤った場合では、次の対応が異なるためである。

### 1.3 分からない場合

`分からない` を押した場合は、解説を表示する。

その後、本人は次から選ぶ。

- `分かった`
- `もう少し説明して`
- `まだ分からない`
- `大人と確認する`

`もう少し説明して` では、問題形式に応じて説明方法を選べるようにする。

- もっと簡単な言葉で
- 具体例を使って
- 途中の手順を細かく
- 似た簡単な問題から

PoC では補足説明を最大 10 回まで許可する。何回で理解へ収束するか、どこで離脱するか、10 回へ到達する問題があるかを観測する。

10 回へ到達した場合や、本人が途中で希望した場合は、大人との確認対象に回す。

### 1.4 おかしい・納得できない場合

子ども向けには、問題文、画像、模範解答などへの違和感を報告する `おかしい・納得できない` を用意する。原因分類は任意とし、問題不備が疑われる場合は、その問題を即時停止して大人の確認へ送る。

AI 採点を使う問題では、採点結果の近くに `AI 採点に不服` を別途用意する。AI とその場で口論させず、個別の採点結果を保留して大人の確認へ送る。AI 採点への異議だけでは、問題そのものを停止しない。

押された場合は次の情報を保存し、学習自体は止めない。

- 問題
- 回答
- AI の判定
- AI の判定理由
- 問題テンプレート
- 発生日時

大人が子どもと口頭で確認し、次のいずれかへ分類する。

- AI 判定が誤り
- 元の判定でよい
- 問題が曖昧
- 判断できない

アプリ内で長い説明文を書かせない。テキストコミュニケーションへ置き換えるより、直接会話する方が解決しやすい。大人の確認結果に対する再異議フローは作らない。

問題不備が確認された場合は、その問題と関連する採点結果を集計対象から外す。AI 採点への異議が未解決の場合は、個別の採点結果だけを保留する。

## 2. 一巡と再学習

未解決箇所があっても、基本的には教科書順で先へ進む。

理由:

- その箇所だけが分からない場合がある
- 先へ進むことで理解が進む場合がある
- 最初から完全理解を求めると、全体を走り切れない可能性がある

一巡後は、原則として最初につまずいた箇所から戻る。後続問題の基礎になっている可能性があるためである。

再学習では、未解決箇所に関する基礎問題から始め、少しずつ難易度を上げる。つまずいた原因を探る場合は、複数の観点へ分けるが、検証は一つずつ行う。

例: 文章題

1. 基礎的な計算ができるか
2. 問われている内容を読み取れるか
3. 式を立てられるか
4. 計算結果を答えとして表現できるか
5. 応用条件が加わっても解けるか

診断では、最初の失敗だけで止めず、いったん全観点を確認する。局所的な問題か、ある地点以降すべてで失敗するのか、複数観点で独立して失敗するのかを見分ける。

再学習の完了条件は、応用を含む最も難しい水準の類題へ回答できることとする。ただし、一問の正解だけで長期定着を保証できるわけではない。定着は後日の確認問題や実力テストで別に測る。

## 3. 理解度の測定

### 3.1 三層の記録

- 通常学習の記録
- 通常学習へ混ぜる基準問題による継続的な推定
- 明示的な確認テストによる、より信頼度の高い測定

本人には、統計的な事実として分野ごとの正答率や変化を示す。

例:

| 分野 | 推定水準 | 安定性 | 根拠 |
|---|---:|---|---|
| 一次方程式 | 92% | 安定 | 直近 4 回: 90, 95, 90, 93 |
| 三次方程式 | 71% | 不安定 | 直近 4 回: 45, 92, 58, 89 |

単純な平均値だけではなく、出題数、期間、難易度、安定性を合わせて扱う。データが少ない場合は、傾向を断定しない。

### 3.2 確認テスト

確認テストは本人へ明示する。

完全任意だけでは、いつまでも傾向を測れない可能性がある。一定の区切りで受験を促す。一度に行うのが難しい場合は、通常問題へ基準問題を少しずつ混ぜ、推定水準を更新する。

通常学習へ基準問題が含まれることを本人へ明示するかは、現時点では低優先度の保留事項とする。

### 3.3 テスト対策

テスト対策では、まず試験範囲全般を対象に最新の実力テストを行う。

その結果を基に、次を組み合わせて重点復習する。

- 実力テストで誤答した分野
- 結果が不安定な分野
- 解答時間が長い分野
- 忘却が疑われる分野
- 本人が不安だと申告した分野

実力テスト中には、本人が任意で `不安` マークを付けられるようにする。感覚が残っている時点で記録する。

得意分野も完全には除外せず、最低限の確認問題を出す。ただし、得意分野を繰り返すこと自体を目的にしない。

問題数や学習時間は初期段階で固定しない。小学校と中学校ではテストの位置づけや負荷が異なるため、一つのレイヤーへ並べて決めるのは早計である。

## 4. 教材管理

教材管理には Obsidian Vault を使う。

Vault は、教科のカテゴリ、単元、Skill、前提関係、関連性を人が編集しやすい形で管理する入力元として扱う。学習履歴やアプリ内部状態とは分ける。教材コンテンツそのもの（実教科書由来の問題など）は著作権を含むため、本リポジトリには含めず、リポジトリ外で管理する（[9. データ配置](#9-データ配置) を参照）。

Vault 内の Markdown は Obsidian で扱う。公開リポジトリ内の文書は、引き続き標準 Markdown リンクを使う。Obsidian 固有記法や Mermaid の注意点は [AGENTS.md](../../AGENTS.md) に従う。

### 4.1 単元ノート

教材管理の入口は教科書の単元とする。出題選定と習熟度の観測では、必要最小限の Skill を単元へ紐付ける。細かな Skill 分解は、運用して必要性が見えてから追加する。

```yaml
subject: 算数
textbook: 教科書名
unit: 分数のたし算
pages: 42-47
order: 12
prerequisites:
  - 分母
  - 同分母のたし算
```

本文には、単元概要、問題テンプレートへのリンク、必要な補足を置く。

単元ノートと Skill ノートの関連性は、Vault 内では Obsidian のリンクで表現できる。アプリが利用する ID、順序、前提 Skill は frontmatter にも保持する。

### 4.2 問題テンプレート

問題テンプレートは単元ノートと分ける。

```yaml
unit: 分数のたし算
difficulty: 基礎
aspect: 通分
answer_type: numeric
grading: deterministic
status: active
```

本文には、問題文テンプレート、正答条件、解説方針、必要に応じて類題生成ルールを置く。

AI が生成したすべての類題を Vault へ保存しない。採用済みテンプレートと、品質改善に必要な代表例だけを残す。

### 4.3 具体問題

実際に出題する具体問題は、Markdown ではなく JSON Entity として DATA_DIR に置く。問題を大量に読み込み、待機列へ積み、回答イベントと紐付けるためである。

```yaml
id: q-001
subject: 算数
unitId: fraction-addition
skillIds:
  - same-denominator-addition
questionType: numeric
body: 1/4 + 2/4 = ?
answer:
  type: exact-text
  value: 3/4
source:
  type: ai-generated
  templateId: same-denominator-basic
reviewStatus: auto-approved
purposes:
  - learning
  - review
assessment:
  equivalenceGroupId: fraction-addition-basic-001
  relation: isomorphic
```

評価問題を別フォルダへ分離せず、`purposes` と `assessment` を Question Entity の属性として持たせる。評価セットや条件が変化しても、Question Entity と評価プロトコルのバージョンで追跡できるようにする。

`questionType` の `numeric`、`free-text` などは JSON・API で使う安定した内部値として保持する。
利用者向け画面では、内部値だけを表示せず、`数値回答（numeric）`、`自由記述（free-text）` のように
日本語ラベルを主とした二重表記にする。また、`skillIds` は習熟度推定や出題選定に使う内部分類であり、
通常の利用者へ ID の自由入力を求めない。単元に登録済みの Skill を自動付与するか、表示名から選択する。

### 4.4 問題生成

人間が全問題を手作業で用意する方式は継続できない。一方、AI 生成問題を無検証で出題するのも危険である。

共同作業として次の流れを想定する。

1. 教科書の単元と学習目標を登録する
2. AI が問題テンプレート、類題、解答、解説を生成する
3. 人間が代表的な問題を確認して採用する
4. 採用済みテンプレートから、AI が数値や条件を変えた類題を作る
5. 自動検証できる問題は、計算や制約チェックも通す
6. 問題が見つかったテンプレートは停止候補にする

AI 生成問題を自動承認できるかは、問題分類と採点方式で判断する。

| 分類 | 初期方針 |
|---|---|
| 数値計算 | 正答と制約をローカル検証できる場合は自動承認候補 |
| 漢字 | 対象学年や対象集合を機械的に制約できる場合は自動承認候補 |
| 選択式 | 問題文、選択肢、正答を機械検証できる範囲で自動承認候補 |
| 文章題 | 表現の曖昧さがあるため、人の確認を基本とする |
| 自由記述 | 複数の正答表現があり得るため、人の確認を基本とする |
| 手書き、音声 | 認識と採点の妥当性確認が必要なため、人の確認を基本とする |

自動承認は、単に分類名だけで許可しない。各テンプレートが持つ検証器を通過した問題だけを対象にする。

## 5. 難しい問題形式の探索

初期 PoC でも、難しい形式を少数ずつ試す。

| 対象 | 主な検証課題 |
|---|---|
| 算数・数学の文章題 | 問題生成、立式、途中式、解説 |
| 漢字の書き取り | 手書き入力、字形認識、許容範囲 |
| 英語の記述問題 | 文法、意味、複数の正答表現 |
| スピーキング | 音声認識、発音、流暢さ、意味の評価 |

最重要の評価軸は、子どもが AI の判定へ納得できるかどうかである。

ただし、納得しやすいことと判定が正しいことは別である。AI 判定、人間の判定、本人の異議を分けて記録する。

## 6. 学習履歴

集計済みの正答率だけでなく、一問ごとのイベントを保存する。

最低限の記録候補:

```text
日時
学習者
単元
問題テンプレート
実際の問題文
学習者の response（テキスト、選択肢、手書き画像、音声、未回答）
判定結果
回答時間
不安マーク
分からないボタン
納得できないボタン
補足説明の回数と種類
大人による確認結果
```

手書き画像やスピーキング音声は、本人と保護者の合意を前提に PoC ではローカル保存する。保存目的は AI 判定の妥当性確認であり、削除できるようにする。

### 6.1 離脱の観測

開始率だけでなく、どこで負荷を感じて離脱したかを観測する。

- 画面を見たが開始しなかった
- 問題を見て中断した
- 回答入力の途中で止めた
- 採点待ちや結果表示で離れた
- 一問を完了し、自分で終了した
- 追加問題へ自然に進んだ
- 問題形式、難易度、所要時間、入力方法
- 翌日以降に戻ったか

一問を完了して本人が終了を選んだ場合は、短時間でも成功として扱う。

中断後の再開方法は、現時点で安易に固定しない。実際の傾向を見て模索する。

## 7. 大人向けレポート

### 7.1 日次レポート

学習終了時に、大人向けの日次レポートを生成する。同日に再開した場合は更新する。

本人には見せない。

候補:

- 今日取り組んだ単元
- 問題数、正答数、所要時間
- 前回までとの変化
- 同種の誤答傾向
- 中断した箇所
- 本人が付けた不安マーク
- `分からない` が押された問題
- `納得できない` が押された問題
- 大人との確認が必要な項目

人格評価はしない。例えば `注意力がない` ではなく、`符号が異なる回答が 3 件ありました` のように観測事実を示す。

レポートの詳細度に唯一の正解はない。大人の期待値によって変わるため、PoC で少しずつ試す。

### 7.2 週次レポート

日次では見えにくい傾向を確認するため、直近 7 日間の週次レポートも将来候補とする。

- 単元ごとの正答率と変化
- 繰り返している誤答傾向
- 未解決の確認事項
- 学習量の推移
- 補足説明が収束しにくい問題形式

### 7.3 外部共有

保存の中心はローカルとする。共有方法として、メール添付や Google Drive へのファイル送信を候補に残す。

外部共有は必須機能ではなく、今後の課題とする。

## 8. 自由チャット

本アプリ上に、codex app-server を使った自由チャット画面を、子どもの自己学習を深掘りするサブ機能として用意できる可能性がある。

- 通常学習とは別導線にする
- 分からない部分を深掘りする用途にも使える
- 学習途中から入った場合は、元の問題へ戻れるようにする
- 会話履歴はローカルに残し、学習の参考情報として使う
- 大人向け日次レポートには含めない
- 会話内容を自動的に成績へ反映しない

自由チャットから通常学習へつなぐ導線は将来候補とする。本人が希望した場合に、関連する簡単な問題を一問試す程度から検討する。

## 9. データ配置

実データ（学習者の記録・教材コンテンツ）は本リポジトリには置かない。個人情報と著作権を含むため、リポジトリ外の DATA_DIR（例: Windows なら `%APPDATA%/MyManabi`、または設定可能なパス）に置き、アプリがそこを読み書きする。

リポジトリに含めるのは、データ形式を示す合成データ（将来追加する `examples/`）とスキーマのみとする。

DATA_DIR のたたき台:

```text
<DATA_DIR>/
  content/
    units/
    skills/
    templates/
    questions/
  learners/
    learner-a/
      events/
      reports/
      media/
    learner-b/
      events/
      reports/
      media/
```

教材テンプレートは共通領域（`content/`）に置く。学習者別フォルダへ複製しない。

### AI サービスの学習利用設定（利用者が必ず行う）

本アプリは外部 AI サービス（ChatGPT / Codex 等）に教材や問題を送信する。著作権保護の観点から、**利用者は各サービスで入力データをトレーニングに使用しない設定を行うこと**。

- ChatGPT: 設定 → データコントロール → 「全員のためにモデルを改善する」をオフ

教材・学習データのリポジトリ外隔離（DATA_DIR）はアーキテクチャで保証しているが、AI サービスへの送信時の扱いは利用者側の設定に依存する。利用開始前に確認する。

将来のリポジトリ構成（コード追加時）:

```text
MyManabi/
  src/        アプリ本体
  examples/   DATA_DIR の合成データ例（個人情報を含まない）
  docs/       本ドキュメント
```
